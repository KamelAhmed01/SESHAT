# SESHAT navigation revamp: Google Maps reconnaissance and build plan

**14 November 2026, Cairo time · Execution plan updated against `e8797a5`**

**Implementation checkpoint.** The new route UI at `/` opens over Ali’s full 25-chunk Jezero area in 2D and 3D. Stops can be picked in either outer ring or entered by grid coordinate. Routes use terrain where the bundle has valid samples, and the existing scenario decides whether each round trip meets reserve requirements. The return frontier still covers the central 20 m grid. The previous interface is at `/dev/`. Section 9 records observations from the baseline before implementation.

**Recommendation:** Make the route the workbench. It should answer, in order: **Where am I going? What will I encounter? Can I get back within the model’s limits? What do I do next?** During travel, apply a valid detour as soon as it is computed and alert the operator with the reason and the next instruction. Bring the changed section into view on the map. Emphasize the updated route and show the previous path faintly for context. The execution plan places the current workbench at `/dev` as the development menu and the new navigation UI at `/`.

Four source findings matter more than a new visual theme:

1. [`LeafletGrid`](../src/components/cartography/LeafletGrid.tsx) already draws traveled, previous, planned, return, hazard and position marks. Planned and previous polylines are noninteractive. Start by linking existing geometry to the itinerary and profile. Draw the old-only and new-only parts during review; overdraw currently makes some changes hard to see.
2. [`ChangeReview`](../src/components/workbench/MissionLifecycle.tsx) already lists added/deferred/shortened stops and reserve deltas for ordinary reviews. The interrupted-stop branch has its own comparison. Give both one set of comparison fields and preserve their different actions. Selection in either branch must preview the exact option that would be applied.
3. [`remainingActivePlan`](../src/engine/lifecycle-store.ts) trims travel at the current cursor and accounts for consumed science; the review calls it on the updated execution. It is a rendering/comparison input, not an immutable snapshot of what the crew saw before the event. The old route may cross a new hazard and uses the old plan pace. Do not label a mixed-bookkeeping delta “minutes saved by rerouting.” Capture or reconstruct the necessary states explicitly.
4. The live [frontier](../src/engine/frontier.ts) checks time, oxygen and battery and uses a standard science-stop duration. The nearby-target [ledger](../src/engine/opportunity-ledger.ts) currently calls the time-based target assessment with position and hazard inputs. Label that preview by its basis. A site can look reachable in the time-only list without fitting the current multi-resource itinerary; an `Add to route` suggestion must evaluate the actual insertion.

## 4. One map, five reading modes

Desktop: preserve the existing map beside a decision rail. Put the selected route summary at the top of the rail, the route steps immediately after it and the approval or progress action in a predictable place. Keep settings, source drawer, and secondary exports a level down. Mobile: map plus a bottom sheet with a readable collapsed state (next action, current/next stop and reserve) and an expanded itinerary. Fit to the visible map area, account for the sheet and safe-area insets, and keep a keyboard path for every map action. At small widths compare alternatives one at a time with the important fields aligned, rather than compressing two full cards.

| Mode | Main read | First action | Map treatment |
|---|---|---|---|
| Plan / locked | Start, stops, “Return to Landing Site,” route choice, round trip and modeled return margin | Add a stop → Preview route → Lock plan → Start rehearsal | Show the entire route and numbered stops. Mark return with a distinct pattern and label, even where it retraces outbound geometry. |
| Travel / return | “Next: [action]” with distance, modeled time, and the closest relevant constraint | Advance rehearsal / Arrive at stop / Reach Landing Site | Mark position, next leg and direction. Show the next part of the leg first; `Overview` restores the whole route. |
| At a stop | “[Activity] at [site]”, elapsed/planned work, observations, and what comes next | Continue fieldwork / Complete stop | Anchor at the stop; keep onward and return links visible on demand. |
| Review / hold | When a valid detour cannot be applied or a mission decision is needed, show the reason, affected leg and available actions | Review options / Hold / Review direct return | Keep the position marker at the current cell. Style any preview separately from the active route. |
| Complete | Returned, completed/partial/deferred work, remaining resources and change history | Download or print | Fit traveled track and recorded events. Show accepted revisions in history. |

### The route should explain itself

- Make the itinerary an ordered strip of **go → do → go home**, rather than a single arrow-delimited string. Each step has a stable link to a leg and an ordered cell span. Label the start, named science sites and the base at minimum. Put `Here`, direction, and `Return to Landing Site` on the map itself. Use line style plus text or symbols, so outbound, return, completed and changed are distinct without color.
- Divide a leg at operator decisions: departure, meaningful terrain change, scenario hazard affecting the path, arrival, or a contingency point the engine can support. Derive marks from ordered AEQD cells and audited inputs. Merge runs of grid bends; the route has no street turns. Avoid bearings or left/right commands until there is an agreed, verified meaning and source. A simple instruction can be “Follow the highlighted leg to [site].” Attach measured distances and model grades only when supported.
- Put the localized cue before its source details. Example template: “Steeper section ahead · [distance along route]. Keep to the highlighted route.” Detail: grade sampled from the DTM, its resolution, and the scenario basis. Distinguish **terrain feature modeled**, **scenario exclusion**, **historical context** and **unknown**. Thermal inertia may suggest a proxy comparison; it cannot establish traction, material, sinkage, or ground-level clearance. Never promise the route is clear of small obstacles from these data.
- During progress show only the next relevant callout on the active line. Use map/list/profile linked selection; click, touch and keyboard selection give equivalent information. Keep hover an enhancement. At high zoom separate labels with offsets or collapse nonessential labels; at low zoom combine them into a waypoint summary. Show source/evidence in a detail affordance and put essential warnings on the route and in the reading order.
- Suggested first-read labels over existing states: `Fits all modeled paces` (ROBUST), `Fits only some modeled paces` (MARGINAL), a specific `Reserve shortfall` or `No supported path` (INFEASIBLE reasons), and `Cannot evaluate` (UNKNOWN). Maintain canonical enum names in details and archives. Say “above reserve at slower modeled pace” when that is the metric; show oxygen and battery in a labeled breakdown, not an unlabeled series of values. Keep the two-tier frontier: `Can stop for science and return` and `Can pass through and return` under the model. Areas and the number of affected targets are separate summaries.

## 5. In-progress change: the main redesign

### What the operator sees

1. **Switch and alert in the same update.** When the route inputs show a deviation or a reported hazard blocks the path, calculate from the current supported cell. A detour qualifies when its directed path is supported, it keeps the current stops and activity plan, and it meets all modeled return reserves. Use the existing route preference to rank qualifying detours and apply the best one as soon as it is ready. Keep the crew position, recorded travel and fieldwork. Use the position and event inputs available to the app.
2. **Put the next action above the explanation.** Use a persistent, announced message such as “Route updated. Follow the highlighted route to Hazeltop. A reported blockage cut off the previous path.” Add the estimated time or reserve change when comparable. `View changes` opens the detailed comparison. The alert and route stay in the map view. Keep the alert and faint previous path visible until the user dismisses the alert. After dismissal, the route history retains the reason, revision and geometry for `View changes`. Give the same next instruction in the map and itinerary.
3. **Bring the changed route into focus.** Pan or zoom once so the next instruction and the divergence between the old and new paths are visible. Highlight the new segment and draw the superseded segment faintly with the label `Previous path`. Draw shared geometry once. Keep `Overview` available to show the whole route. Use an instant fit with reduced motion. When geometry stays the same, keep the current view and explain the timing, activity or reserve change. An event farther behind the crew or off the remaining route can update history and reserves while preserving the active route where the engine supports it.
4. **Show recovery options when a detour fails.** If position, terrain support or return reserves prevent a validated detour, withhold the blocked next instruction and state the specific reason. Keep the blocked stop in the itinerary and mark why it cannot be reached. Show evaluated options such as skipping the stop, changing the activity, or returning directly when those options are available. Apply a change to planned stops or activity only when the user chooses it. Apply only a candidate evaluated against the latest event, crew position and bundle. The alert, map and history should reflect the same active revision.

### Use three comparisons with named baselines

All comparisons start at the same **route position and progress point**. Preserve the original accepted plan. This proposal does not change any model formula.

| View | Definition | What it can say |
|---|---|---|
| **Before the event** | Remaining accepted itinerary at the instant before recording, including activity already spent, pre-event conditions and matching scenario/model revision. | “Before the delay, [margin] above reserve.” |
| **If we keep the plan** | Re-evaluate that same remaining path and sequence with the event applied. Charge delay/resource use once and update pace once. Validate the fixed path against current support and known exclusions; do not silently run route search in this view. | “Keeping this path would cross the reported exclusion,” or “A 15 min delay reduced time above reserve by 15 min,” if the applicable rounded values support it. A blocked/unknown path has no comparable arrival or margin. |
| **If we take this option** | Use the selected evaluated candidate with the same post-event spending, origin, pace basis, constraints and scenario. Work that the option elects to finish counts once. | “This reroute restores [margin] compared with keeping the plan” only when both values are comparable; otherwise state the changed path/stop and the candidate’s own margin. |

Store or deterministically reconstruct these views from existing lifecycle data when possible. Pin event, proposal, accepted revision and bundle identity so refresh or a second event cannot mix versions. Start with a derived UI view model and the existing archive; if exact historical comparisons cannot be reproduced with the current contract, bring a minimal snapshot proposal to the owner before changing persistence schemas or the export contract. Avoid redefining “reserve,” changing the 0.8×/1×/1.2× grid, or adding a hazard threshold to presentation code.

**Geometry comparison:** compare ordered directed edges of the remaining legs at full grid fidelity; only then simplify the drawing, if necessary. Retain selected/changed endpoints, significant cue boundaries and event marks. Reversed traversal, a repeated edge on later legs, and two branches with the same length are different cases; compare by leg occurrence and order rather than a set of coordinates or rounded summary. Never use display projection or decimal lat/lon tolerance to decide whether paths differ. Retain the existing Mars geographic viewer transform and `CRS.Simple` formula; new marks must use the same path to display. Review both route overlap and semantic changes (added/removed/reordered stops, activity time and updated hazards).

**Rehearsal example, from S06:** At Swift Run, a simulated reading adds a proposed follow-up after Hazeltop; both displayed branches list that same downstream sequence. Put the common route on screen once. Beside it: `Finish Swift Run first: 20 min more fieldwork; +20.7 min above time reserve at the slower modeled pace.` The other branch: `Leave Swift Run now: 20 min more above time reserve than finishing; retain any work already recorded.` The captured run had no observations yet, so it should say `0 / 20 min completed` and not imply work was done. Exact candidate values stay linked to the selected branch. After approval show `Swift Run completed · Follow-up added after Hazeltop · Next: travel to Hazeltop`. More detail can explain the model’s Earth-communication assumption; it does not precede the operational choice or imply a real transmission.

### Baseline findings before implementation

1. **Resolve unsupported endpoints before routing them.** The engine currently clamps outer coordinates to its search grid, then substitutes original endpoints back into the result. A direct probe with the committed data returned `READY` and 840 m from `[90,658]` to `[90,700]`, beyond the supported outer coordinate range. A separate probe returned `ROBUST` with a zero-distance leg when a target was marked `APPROXIMATE_REGION`, because itinerary construction falls back to the current cell when the target cell is missing. The same builder labels a non-base origin `Landing Site`. The planner needs explicit footprint, mask and target-confidence checks before the new UI can accept a route. The UI must reflect the resulting status and use the actual origin label. Test exact edges, NoData, unsupported locations and origin at the same point. [Neighborhood routing](../src/engine/traverse-graph.ts#L141) · [Itinerary evaluation](../src/engine/multi-leg-planner.ts#L111)
2. **Validate the route drawn and charged, including at the seam.** The neighborhood search uses 40 m nodes. It substitutes endpoints and expands the returned geometry into smaller steps before reporting distance and time. Search elevation and later edge sampling differ. Missing elevation can become zero rise in step metrics. Prove the final directed geometry, endpoint connectors, hazard intersections, both masks and slope checks against one metric route calculation. An independent geodesic oracle and matching map/profile paths are part of this check. Any claim about “fastest” or gentler/thermal tradeoffs needs evaluated candidates: neighborhood search adds a slope penalty and the planner passes a boolean for lower slope, with no distinct outer thermal search. Bring any model/contract change to the owner separately. [Neighborhood search and geometry](../src/engine/traverse-graph.ts#L223) · [Preference dispatch](../src/engine/multi-leg-planner.ts#L93)
3. **Mark imagery, routing and frontier coverage separately.** Committed neighborhood files describe a 550 × 550 grid at 40 m across a 22 × 22 km area. The live frontier still indexes the central 20 m grid. In the probe, both route directions between the base and `[86,280]` were `READY`, while the frontier from that outer point had no reachable cells to display. That is a limit of the coverage calculation, and `READY` only reports that a path was found. In the new UI, make the central frontier boundary explicit. Keep broader routing offered only for validated input and geometry. When optional files fail integrity, keep 2D route planning usable where core support remains and show a clear availability state for the broader coverage. [Frontier calculation](../src/engine/frontier.ts#L50) · [Optional bundle loader](../src/data/loader.ts#L255)
4. **Reuse one route state in both renderers.** The current 3D view draws planned and traveled geometry, and selecting a point calls both inspect and select. Its route drawing does not show previous segments, exclusions or the active position, and **Fit mission** switches to 2D. Use the 2D map and route list for the first release slice. Wire 3D to the same route state and selection through an optional preview once its map parity, coverage and input checks pass. Check visible terrain picking against the manifest, keyboard/touch selection and missing textures. [3D drawing and picking](../src/components/cartography/Mars3DView.tsx#L612) · [Map controls](../src/components/workbench/MissionLifecycle.tsx#L1158)
5. **Match evidence labels to the manifest.** The source drawer has a “Verified PDS sample targets” label, while the active [manifest](../public/data/manifest.json) records `SOURCE_REVIEW_REQUIRED`, `coordinateFrameVerified: false`, and `challengeResourceQualified: false`. The ledger records listed and used resources. Show source-reported locations, datasets in use and outstanding review as separate facts.
